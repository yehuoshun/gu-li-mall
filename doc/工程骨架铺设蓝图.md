# 谷粒商城工程骨架铺设蓝图

> 2026-11-01 · 配套根 pom（`com.shun.gu_li_mail`）的铺设指南
> 原则：**骨架先行，版本占位，BOM 留空**——旧代码（Boot 2.2 时代）搬进来时保持可编译可跑，升级留到阶段 1 逐模块做。

---

## 一、核心原则（为什么这样铺）

1. **根 pom 现在是纯聚合壳**，不定义 parent / properties / dependencyManagement 的实质内容——因为旧模块代码还是 Boot 2.2 时代，一旦根 pom 钉上 Boot 3 全家桶，搬进来的第一批代码会**当场编译崩溃**，把「先跑起来」硬变成「边搬边升级」。
2. 对应节奏：**阶段 0（搬代码、先跑）→ 阶段 1（升级 Boot 3）**。骨架期只负责把目录和构建关系立起来。
3. 每个阶段只做一件事，每件事可回滚。

## 三、根 pom 蓝图（✅ 2026-11-01 策略更新：Boot 3 家族直上）

> **策略变更**：不走「旧代码先跑 → 再升级」，而是**新工程直接 Boot 3.5 家族，搬入即适配**（老板拍板，已落地）。代价：common 等模块搬进来那一刻就要完成 Boot 3 适配（javax→jakarta、fastjson 清除、MP boot3 starter 等），阶段 1 的升级工作与代码搬运合并。

| 区块                                       | 骨架期（现在）                                                       | 搬代码时（搬入即适配）                                |
| -------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------- |
| `<packaging>pom</packaging>`               | ✅ 已有                                                               | —                                                     |
| `<modules>`                                | ✅ 已写全 12 个                                                       | 随目录同步                                            |
| `<parent>`（spring-boot-starter-parent）   | ✅ **3.5.16**（用 `<parent>` 方式，**不是** dependencyManagement）    | 子模块自动继承                                        |
| `<properties>`                             | ✅ Java 17（建议抽到根 pom 统一，子模块删重复）                       | 补各 BOM 版本                                         |
| `<dependencyManagement>`                   | ✅ SCA 2025.0.0.0（import）+ SC 2025.0.0（**记得 scope=import**）     | 按模块批次补充单点兜底（springdoc/redisson/es/oss）   |
| `<description>` 等                         | ✅ 已有                                                               | —                                                     |

**根 pom 目标形态**（示意，落地由开发者写）：

```xml
<packaging>pom</packaging>
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.5.16</version>
</parent>
<modules>...12 个...</modules>
<properties>
    <java.version>17</java.version>
</properties>
<dependencyManagement>
    <dependencies>
        <!-- Boot 全家桶版本已由 parent 提供，无需重复 import -->
        <dependency>
            <groupId>org.springframework.cloud</groupId>
            <artifactId>spring-cloud-dependencies</artifactId>
            <version>2025.0.0</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
        <dependency>
            <groupId>com.alibaba.cloud</groupId>
            <artifactId>spring-cloud-alibaba-dependencies</artifactId>
            <version>2025.0.0.0</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

> ⚠️ 两个常见坑：① `spring-boot-starter-parent` **不能**放进 dependencyManagement（它是 parent 不是 BOM，放了不生效）——要管 Boot 版本就用 `<parent>`，或用 `spring-boot-dependencies` 的 import；② BOM import 必须写 `<scope>import</scope>`，漏写则整段无效。

> `<module>` 标签写**相对目录路径**，所以旧课程目录名（gulimail-/gulimall-/gilimall- 拼写混乱）也能聚合——但既然是新骨架，建议**直接按上表新命名建目录**，从 Gitee 旧仓库**复制内容**而非复制名字。

## 四、每个模块的骨架文件清单（空壳模板）

每个模块 4 件套，全部建好即可 `mvn clean install` 通过（空壳构建 0 文件也能过）：

| 文件                                           | 内容要点                                                                                                                                                      |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pom.xml`                                      | `<parent>` 指向根 pom（`com.shun.gu_li_mail:gu_li_mail:0.0.1-SNAPSHOT`，relativePath 默认 `../pom.xml`）；artifactId 用新名；**依赖留空或仅从 common 继承**   |
| `src/main/java/.../XxxApplication.java`        | 启动类 + `@SpringBootApplication`（包名先用课程原样，见决策 D3）                                                                                              |
| `src/main/resources/application.yml`           | 占位：`spring.application.name` + `server.port`（沿用课程端口表）+ nacos 地址注释                                                                             |
| （可选）`src/test/.../ApplicationTests.java`   | 空测试占位                                                                                                                                                    |

**搬旧代码时每个模块的最小改点清单**（从 Gitee 仓库复制进来后必改 3 处）：

1. pom 的 `<parent>` → 新根 pom（原来指向课程根 `com.atguigu.gulimail:gulimail`）
2. 依赖 `gulimall-common` 的坐标 → `com.shun.gu_li_mail:gu-li-mall-common`（等 common 改名后）
3. 涉及自研 jar 的 `<dependency>` 版本号若引用课程 properties → 清理

> Java 包名**此行不动**（仍是 `com.atguigu.*`），等 D3 决策。

## 五、铺设节奏建议（两轮）

**第 1 轮（先通构建链）**：只铺 `common` 一个模块
- 建目录 + 4 件套 → 从 Gitee 旧仓库 `gulimall-common` **只复制 `src/`** 和 pom 依赖列表 → 改 parent 指向新根 → `mvn clean install` 过
- 验收：根目录 `mvn -pl gu-li-mall-common install` ✅

**第 2 轮（铺满 + 冒烟）**：其余 11 个空壳目录 + pom 全建 → 根 pom `<modules>` 写全 12 个
- 验收：根目录 `mvn clean install`（12 个模块全绿）✅

之后进入阶段 0：按 `common → product → 其余` 逐模块搬业务代码。
